# Wave 1 — Auth + Multi-Device Design Spec

**Status:** Approved (2026-05-20)
**Wave:** 1 of 9 in Sub-project 1 (vertical slice)
**Parent spec:** `docs/superpowers/specs/2026-05-20-mvp-vertical-slice-design.md`
**Builds on:** Wave 0 (`tag: wave-0-complete`)

---

## Goal

Bring auth alive for all three roles (viewer, producer, admin) and ship the multi-device capacity (N=2 cap, 90-day cooldown) end-to-end across backend, web portals, and Android. Done means:

- A viewer signs in on Android via phone OTP (mocked OTP printed to backend logs).
- A producer registers and logs in to a web dashboard that shows their unverified state.
- An admin logs in to the admin web portal and can reach a user's device list to force-deactivate a lost/stolen phone.
- The N=2 device cap is enforced and exercised: a 3rd device attempt returns 409 with the existing devices; the user picks one to deactivate via Android UI; verify succeeds atomically.
- A force-deactivated device's app wipes its local state and shows the "signed out" screen on the next API call.

## Non-goals

- Refresh tokens (24h access token only; re-login on expiry).
- Producer email OTP for sensitive actions (deferred to DRM cycle when Termii lands).
- Email verification on producer registration (deferred to DRM cycle).
- Global API rate limiting beyond OTP attempt tracking (deferred to production cycle).
- Password reset flow (deferred to DRM cycle).
- Server-side JWT revocation / denylist (deferred to production cycle).
- Producer accept-Distribution-Agreement flow (Wave 2).
- Admin verify-producer action (Wave 2).
- Real producer dashboard with charts (Wave 8).
- Real admin platform dashboard (Wave 8).
- Full admin user index with search (Wave 8). Wave 1 has only a tiny `/admin/users` phone-lookup page.
- Inline rename of device `display_name` (deferred to Wave 7 polish).
- Multi-device for producers (browsers don't have device-cap concept here).

## Architecturally significant decisions

| Decision | Choice | Why |
|---|---|---|
| Token strategy | 24h access JWT only, no refresh. | Slice scope; UX cost is acceptable in dev. Refresh arrives in DRM or production cycle. |
| JWT location, web | httpOnly cookie. `Secure: env==='production'`, `SameSite=Lax`, `Path=/`, `MaxAge=86400`. | Standard. SameSite=Lax sufficient CSRF protection for slice. |
| JWT location, Android | EncryptedSharedPreferences. Sent as `Authorization: Bearer <jwt>` on every request. | Industry standard. |
| Common dependency | `get_current_principal` reads `Authorization` header first, falls back to `auth_token` cookie. One dep serves both clients. | Avoids parallel dep trees. |
| Admin schema | Separate `admins` table (id, email, password_hash, created_at, suspended). | Distinct identity. Producer table avoids carrying admin-irrelevant fields. |
| Producer OTP for sensitive actions | None in slice. | Deferred to DRM cycle. |
| Email verification on producer register | None in slice. | Deferred. |
| Rate limiting | OTP-only via existing `otp_codes.attempts` column + per-phone request limit (5 per 15 min). | No external rate limiter needed; defer general API limiting. |
| Password rules | Min 10 chars; bcrypt rounds = 12. | Length > complexity. |
| Producer post-register state | Immediately logged in with JWT; lands on dashboard with unverified banner. | UX > marginal security in dev. |
| Default device display_name | `${Build.BRAND} ${Build.MODEL}` auto-generated on Android. Read-only in Wave 1 (inline rename in Wave 7). | Auto-default is good UX; rename is nice-to-have. |
| Device cap remediation API | Single endpoint: `POST /auth/otp/verify` accepts optional `deactivate_device_id` field. First call returns 409 with active devices; client retries with chosen ID. | One round-trip after picker. Cleaner than a separate unauthenticated endpoint. |
| Admin reach to user devices | Tiny phone-lookup page at `/admin/users` (1-input search) → redirects to `/admin/users/{user_id}/devices`. | Makes the panel actually usable in slice without building a full user index. |
| Logout | Clear cookie (web) / clear EncryptedSharedPreferences (Android). No server-side revocation. | JWT denylist deferred. |

### Endpoint surface

| Method | Path | Purpose | Auth |
|---|---|---|---|
| `POST` | `/auth/otp/request` | Send OTP code to phone (mocked to logs). Rate-limited to 5 per phone per 15 min. | None |
| `POST` | `/auth/otp/verify` | Verify code; resolve device; enforce N=2; mint viewer JWT. Optional `deactivate_device_id` body field. | None |
| `POST` | `/auth/producer/register` | Email + password (≥10 chars). Auto-login: returns JWT. | None |
| `POST` | `/auth/producer/login` | Email + password → producer JWT. | None |
| `POST` | `/auth/admin/login` | Email + password → admin JWT. No registration endpoint. | None |
| `GET` | `/me` | Return current principal info by role. Triggers 403 with `reason=device_deactivated` when viewer JWT references a deactivated device. | Any JWT |
| `GET` | `/devices` | List current viewer's devices (active + deactivated). | Viewer JWT |
| `POST` | `/devices/{device_id}/deactivate` | Soft-deactivate; enforces per-user 90-day cooldown. Idempotent. | Viewer JWT |
| `GET` | `/admin/users/lookup?phone=+234...` | Find user by phone (exact match). Returns `{ user_id, phone }` or 404. | Admin JWT |
| `GET` | `/admin/users/{user_id}/devices` | List user's devices. | Admin JWT |
| `POST` | `/admin/users/{user_id}/devices/{device_id}/deactivate` | Force-deactivate; bypasses 90-day cooldown. Body requires `reason: str`. Logs to `admin_actions`. | Admin JWT |

### Detailed flows

**Phone OTP request** (`POST /auth/otp/request`):

1. Body: `{ phone: str }`. Phone format: E.164, must start with `+234`.
2. Count active (`consumed_at IS NULL`, `expires_at > now`) `otp_codes` rows for this phone created in last 15 minutes.
   - If count >= 5: return `429 { "error": "too_many_otp_requests" }`.
3. Generate 6-digit code via `secrets.choice("0123456789")` six times.
4. Hash code with `bcrypt(rounds=12)` (overkill for 6 digits but consistent).
5. Insert `otp_codes` row with `code_hash=hash`, `expires_at=now+10min`, `attempts=0`.
6. Call `OTPProvider.send(phone, raw_code)`. `MockOTPProvider` writes `logger.info("[OTP] %s → %s", phone, raw_code)`.
7. Return `200 { "sent": true }`. Do NOT include expires_at (defense in depth).

**Phone OTP verify** (`POST /auth/otp/verify`):

Two call modes, distinguished by which body fields are present:

- **Mode A (OTP code path)**: `{ phone, code, device_id, display_name?, model?, platform="android" }` — used on first attempt; verifies OTP and proceeds to device resolution.
- **Mode B (verify-ticket path)**: `{ phone, verify_ticket, device_id, display_name?, model?, platform="android", deactivate_device_id }` — used to retry after 409 device_cap_reached, with the user's chosen device to deactivate. Skips OTP verification entirely (the ticket vouches for prior OTP success).

The endpoint distinguishes modes by `code` vs `verify_ticket` presence; if both or neither, return 422.

**Mode A flow** (`code` present):

1. Body: `{ phone, code, device_id, display_name?, model?, platform="android" }`.
2. Find latest non-consumed `otp_codes` for phone. If none → `401 { "error": "invalid_code" }`.
3. If `expires_at <= now` → `401 { "error": "code_expired" }`.
4. If `attempts >= 5` → `429 { "error": "attempts_exhausted" }`.
5. `bcrypt.verify(code, row.code_hash)`. On mismatch: `attempts++` (save row), `401 { "error": "invalid_code", "attempts_remaining": 5 - attempts }`.
6. Find or create `User` by phone. Set `phone_verified=true`.
7. Resolve device (in a transaction with `SELECT ... FOR UPDATE` on the user row to prevent races):
   - Query `user_devices` where `user_id=user.id AND device_id=body.device_id`.
   - **Active row found** (`deactivated_at IS NULL`): update `last_seen_at = now`. Mark OTP `consumed_at=now`. Skip to step 9.
   - **Deactivated row found**:
     - If `now - deactivated_at < 90 days`: do NOT consume OTP (user may retry with different device). Return `429 { "error": "cooldown_active", "unlock_date": deactivated_at + 90d }`.
     - Else: clear `deactivated_at`, set `last_seen_at`. Mark OTP `consumed_at=now`. Skip to step 9.
   - **No row** (new device):
     - Count active devices for user.
     - If count < 2: insert new row with `display_name`, `model`, `platform`. Mark OTP `consumed_at=now`. Continue to step 9.
     - If count >= 2: mark OTP `consumed_at=now` (it has served its phone-ownership-proof purpose). Mint a **`verify_ticket`** JWS: `{ phone, user_id, exp: now+120s, kind: "device_cap_remediation" }`. Return `409 { "error": "device_cap_reached", "active_devices": [{id, display_name, model, platform, activated_at, last_seen_at}, ...], "verify_ticket": str }`. Client retries via Mode B.
8. (continuation of step 7's happy paths joins here)
9. Mint JWT: `{ sub: str(user.id), role: "viewer", user_device_id: str(device.id), exp: now+24h, iat: now }`.
10. Return `200 { "jwt": str, "user_device_id": str, "expires_at": iso8601 }`.

**Mode B flow** (`verify_ticket` present):

1. Body: `{ phone, verify_ticket, device_id, display_name?, model?, platform="android", deactivate_device_id }`. All fields required.
2. Decode `verify_ticket` with `decode_jwt(..., expected_kind="device_cap_remediation")`. On invalid signature, wrong kind, or expired: `401 { "error": "invalid_verify_ticket" }`.
3. Verify ticket's `phone` matches body `phone`. Mismatch → `401 invalid_verify_ticket`.
4. Load `User` by ticket's `user_id`. (Must exist; if not, `401 invalid_verify_ticket`.)
5. Validate `deactivate_device_id` belongs to this user and is active. If not, `404 device_not_found` or `409 device_already_inactive`.
6. Validate per-user 90-day cooldown not active (look at most-recent `deactivated_at` for this user; if any device deactivated within last 90 days, `429 cooldown_active` with unlock date).
7. In a transaction (`SELECT ... FOR UPDATE` on user):
   - Set `deactivated_at=now` on the chosen device.
   - Insert new device row for `body.device_id`.
8. Mint JWT for new device. Return `200`.

This separation means OTP brute force is fully bounded by the OTP attempt counter (Mode A), and the device-cap remediation cannot be used to bypass OTP (Mode B requires a ticket that can only come from a successful Mode A run).

**Producer register** (`POST /auth/producer/register`):

1. Body: `{ email, password, company_name? }`. Email format validated; password ≥ 10 chars.
2. If email already in `producers`: `409 { "error": "email_in_use" }`.
3. If `len(password) < 10`: `422 { "error": "password_too_short" }`.
4. Hash password with `bcrypt(rounds=12)`.
5. Insert `producers` row with `verified=false`, `agreement_accepted_at=null`, others null.
6. Mint JWT: `{ sub: str(producer.id), role: "producer", exp: now+24h }`.
7. Return `200 { "jwt": str, "producer_id": str, "verified": false }`.

**Producer login** / **Admin login**: standard email+password verify, mint JWT.

**`/me` endpoint** (returns role-specific info):

- Viewer: `{ role: "viewer", user_id, phone, user_device: { id, display_name, model, last_seen_at } }`
- Producer: `{ role: "producer", producer_id, email, company_name, verified, agreement_accepted_at }`
- Admin: `{ role: "admin", admin_id, email }`

**`get_current_principal` dependency**:

```python
async def get_current_principal(
    request: Request,
    db: AsyncSession = Depends(get_db),
) -> Principal:
    token = _extract_token(request)  # Authorization: Bearer header, then cookie
    if not token:
        raise HTTPException(401, {"error": "missing_token"})
    try:
        payload = decode_jwt(token)
    except JWTError:
        raise HTTPException(401, {"error": "invalid_token"})
    role = payload["role"]
    sub = UUID(payload["sub"])
    if role == "viewer":
        device_id = UUID(payload["user_device_id"])
        device = await db.get(UserDevice, device_id)
        if device is None or device.deactivated_at is not None:
            raise HTTPException(403, {"reason": "device_deactivated"})
        user = await db.get(User, sub)
        if user is None or user.suspended:
            raise HTTPException(403, {"reason": "account_suspended"})
        return Principal(role="viewer", user=user, user_device=device)
    elif role == "producer":
        producer = await db.get(Producer, sub)
        if producer is None or producer.suspended:
            raise HTTPException(403, {"reason": "account_suspended"})
        return Principal(role="producer", producer=producer)
    elif role == "admin":
        admin = await db.get(Admin, sub)
        if admin is None or admin.suspended:
            raise HTTPException(403, {"reason": "account_suspended"})
        return Principal(role="admin", admin=admin)
    raise HTTPException(401, {"error": "unknown_role"})


async def get_current_viewer(p: Principal = Depends(get_current_principal)) -> Principal:
    if p.role != "viewer":
        raise HTTPException(403, {"reason": "viewer_required"})
    return p
# similar for producer, admin
```

**Admin force-deactivate**:

1. `POST /admin/users/{user_id}/devices/{device_id}/deactivate`
2. Body: `{ reason: str }`. Required, min 5 chars.
3. Verify device belongs to user. Set `deactivated_at=now`. Bypass cooldown check.
4. Insert `admin_actions` row: `admin_email = admin.email, action="force_deactivate_device", target_type="user_device", target_id=device.id, reason=body.reason`.

### `middleware.ts`

Runs on `/producer/:path*` and `/admin/:path*`. Reads `auth_token` cookie. Verifies JWT signature with `jose` and HS256 against `JWT_SECRET`. Reads `role` claim:

- Producer route + producer role → allow
- Admin route + admin role → allow
- Wrong role → redirect to corresponding login
- Missing/invalid → delete cookie, redirect to corresponding login

The `/producer/login`, `/producer/register`, `/admin/login` paths are NOT in the matcher; they're publicly accessible and the auth/(auth) route group prevents authenticated users from re-rendering them (handled in their layouts via `getServerPrincipal`).

### Form pattern

Each login/register page renders a Server Component shell + a Client Component form. Form uses `react-hook-form` + zod resolver from `lib/validators.ts`. Submit calls a Server Action which:

1. Validates input via zod.
2. Calls backend `/auth/{producer,admin}/{login,register}` via `lib/api-client.ts`.
3. On success: `cookies().set("auth_token", jwt, { httpOnly: true, secure: env === "production", sameSite: "lax", path: "/", maxAge: 60*60*24 })`. Then `redirect("/producer/dashboard")` or `/admin/dashboard`.
4. On failure: throws an error caught by the form; renders error message.

### Producer dashboard banner states

The dashboard is a Server Component that fetches `/me`. Conditional banner:

- `verified === false` → yellow alert: "Your account is awaiting verification. An admin will verify you shortly." No action button.
- `verified === true && agreement_accepted_at === null` → blue alert: "You've been verified. Distribution Agreement signing arrives in Wave 2." **No button in Wave 1** (button hidden; will be added in Wave 2).
- Both set → green check: "Account ready. Upload, films, and payouts open up in upcoming releases."

Below the banner: dashed-border placeholder explaining "Full dashboard arrives in Wave 8."

Sidebar nav items with "Wave N" pills mark not-yet-built features (Films Wave 3, Upload Wave 3, Payouts Wave 8, Settings Wave 9).

### Admin user-devices panel

`/admin/users` (NEW phone-lookup page):
- Single text input for phone (placeholder `+234...`) and Search button.

### Conventions

- **MVVM with `StateFlow`** — each screen has `XxxViewModel` exposing `StateFlow<XxxUiState>`. Composables `collectAsStateWithLifecycle()`.
- **`UiState` sealed classes per screen** — covering `Loading`, `Ready(data)`, `Submitting`, `Error(message)`, plus screen-specific states (e.g., `OtpEntryUiState.WrongCode(attemptsRemaining)`, `OtpEntryUiState.DeviceCapReached(devices)`).
- **Repositories return `Result<T, AlabaError>`** — sealed `AlabaError` covering `NetworkError`, `InvalidCode(attemptsRemaining)`, `CodeExpired`, `AttemptsExhausted`, `DeviceCapReached(devices)`, `CooldownActive(unlockDate)`, `Unauthorized`, `DeviceDeactivated`, `Unknown(message)`.
- **`AuthEventBus`** — singleton `MutableSharedFlow<AuthEvent>(extraBufferCapacity=1)`. `AuthEvent.TokenExpired`, `AuthEvent.DeviceDeactivated`. `MainActivity` collects in `lifecycleScope`.

### Device ID generation

### Auth interceptors

```kotlin
class AuthInterceptor @Inject constructor(private val tokenStore: TokenStore) : Interceptor {
    override fun intercept(chain: Interceptor.Chain): Response {
        val request = chain.request()
        val token = tokenStore.readJwt()
        val newReq = if (token != null) {
            request.newBuilder().addHeader("Authorization", "Bearer $token").build()
        } else request
        return chain.proceed(newReq)
    }
}

class AuthErrorInterceptor @Inject constructor(
    private val authEventBus: AuthEventBus,
) : Interceptor {
    override fun intercept(chain: Interceptor.Chain): Response {
        val response = chain.proceed(chain.request())
        if (response.code == 403) {
            val body = response.peekBody(4096).string()
            if (body.contains("\"device_deactivated\"")) {
                authEventBus.tryEmit(AuthEvent.DeviceDeactivated)
            }
        }
        if (response.code == 401) {
            authEventBus.tryEmit(AuthEvent.TokenExpired)
        }
        return response
    }
}
```

class MainActivity : ComponentActivity() {

                                }
                            }

                            }
                        }
                    }
                }
                AlabaNavHost(navController, startDestination = if (tokenStore.hasJwt()) "signed_in" else "phone_entry")
            }
        }
    }
}

### Device cap reached flow

`OtpEntryViewModel.verify(code)`:
1. Calls `authRepository.verifyOtp(phone, code, deviceId, displayName, model)`.
2. On `DeviceCapReached(devices, verifyTicket)`:
   - Stores `verifyTicket` in screen state (transient — never persisted to disk).
   - Emits one-shot navigation event with the devices payload + ticket.
3. `OtpEntryScreen` collects the event → `navController.navigate("device_cap_reached")` with the devices + ticket passed via a shared `SavedStateHandle` slot.
4. `DeviceCapReachedViewModel.deactivate(deviceId)` calls `authRepository.verifyOtpWithTicket(phone, verifyTicket, deviceId=newDeviceId, displayName, model, deactivateDeviceId=chosenId)`. On success, mints the JWT and navigates to the signed-in graph.

The ticket lives in-memory only and expires server-side in 120 seconds; if the user takes longer than that to pick, they re-enter the OTP code.

### Settings → Devices

`DevicesScreen` Composable lists devices from `DevicesRepository.list()`. Two card sections (active, deactivated). Each active card has a "Deactivate" button. The current device card shows the THIS DEVICE pill. Deactivation flow:

1. Tap "Deactivate" → opens `ConfirmBottomSheet` with appropriate copy (this device vs other).
2. Confirm → call `devicesRepository.deactivate(deviceId)`.
3. On success:
   - If deactivated device == current: emit `AuthEvent.DeviceDeactivated` (MainActivity navigates).
   - Else: refresh the list.
4. On `CooldownActive(unlockDate)`: dismiss sheet, show top-of-screen banner: "Cooldown active. Unlock on {unlockDate}." Update both deactivate buttons to disabled state.

## Risks specific to this wave

- **OTP code mocking is sticky** — if `MockOTPProvider` somehow ships to production, all OTP codes leak to logs. Mitigated by `Settings.environment != "production"` assertion in `MockOTPProvider.__init__`. Tested.
- **Verify-ticket design is novel** — increases attack surface vs. straight OTP-only. Mitigated by: (a) ticket only mintable after successful OTP verify, (b) 120s expiry, (c) tied to phone+user_id, (d) `kind` field prevents misuse as access token.
- **WSL2 emulator-to-host networking** — multi-device testing requires two emulators or one emulator + one real device, both reaching the host backend. Document `make android-url` for real device IP; emulator uses `10.0.2.2`.
- **Inline rename deferred** — Wave 1 has no user-visible way to clean up a "TECNO Camon 18" autonamed device shared by 2 phones with same model. Acceptable; rename arrives in Wave 7.
- **Race conditions on device cap arithmetic** — two concurrent OTP verifies on a user at cap=1 could both succeed, ending at cap=3. Mitigated by `SELECT ... FOR UPDATE` on the user row inside the verify transaction (or equivalent advisory lock).

6. Open the Android app on a SECOND emulator (different device_id). Repeat OTP flow with the same phone number. Both devices shown in Settings → Devices.
7. Try to add a third emulator → app shows DeviceCapReached. Pick one → succeed.
